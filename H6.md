# H6: Onkohan tämä turvallinen käyttää? — TP-Link Tapo C200 -kameran tietoturva-analyysi

---

## 1. Johdanto ja tavoite

Tämän tehtävän tarkoituksena on tutkia TP-Link Tapo C200 -verkkokameran firmwaren
tietoturvaa laitteesta saadun flash-muistin dumpin (`dump-tapo-c200v3-1.4.2.bin`)
perusteella. Tavoitteena on selvittää, millaisia haavoittuvuuksia laitteesta löytyy
ja olisiko niitä mahdollista hyödyntää käytännössä.

Menetelminä käytettiin binwalkia, checksec-työkalua, `strings`-analyysiä ja Ghidra-
takaisinmallinnustyökalua. Työn tukena käytettiin Quentin Kaiserin blogikirjoitusta
"Rooting the TP-Link Tapo C200 Rev.5" (Kaiser, 2025), joka kuvaa vastaavan laitteen
(Rev.5) analyysiä samalla menetelmällä.

---

## 2. Menetelmä

1. Purettiin valmis flash-dump (`dump-tapo-c200v3-1.4.2.bin`, 8 MB) `binwalk`illa,
   joka tunnisti ja purki tiedostojärjestelmän osiot automaattisesti — mukaan lukien
   pääsovellusten `rootfs`-osion Squashfs-muodossa.
2. Toisin kuin Kaiserin tutkimassa Rev.5-laitteessa, tässä versiossa (v3/1.4.2)
   rootfs ei ollut suojattu AES-CFB1-header-salauksella siten, että se olisi estänyt
   binwalkin automaattisen purun — Squashfs-osio tunnistui ja purkautui suoraan
   ilman manuaalista avaimenhakua/purkua.
3. Puretusta tiedostojärjestelmästä analysoitiin pääsovellusbinääri `bin/main`
   (ELF 32-bit MIPS, dynaamisesti linkattu, stripattu debug-infosta mutta symbolit
   pääosin tallella — 1861 funktiota, 1922 symbolia).
4. Binäärin suojausmekanismit tarkistettiin `checksec`-työkalulla.
5. Kiinnostavia toiminnallisuuksia (autentikointi, komentojen suoritus) etsittiin
   `strings`-analyysillä ja tarkasteltiin tarkemmin Ghidrassa (versio 12.1.3,
   MIPS:LE:32).

---

## 3. Löydökset

### 3.1 Binary hardening -suojaukset puuttuvat kokonaan

`checksec`-tulos pääbinäärille `bin/main`:

| Suojaus | Tila |
|---|---|
| RELRO | Ei käytössä |
| Stack Canary | Ei käytössä |
| NX (pinon suoritussuojaus) | Ei käytössä |
| PIE | Ei käytössä |
| Fortify | 0/23 fortifioitavaa funktiota suojattu |

Kaikki neljä nykyaikaista muistin suojausmekanismia puuttuvat samanaikaisesti.
Tämä tarkoittaa, että mikäli binäärissä on hyödynnettävä muistivirhe (esim.
puskurin ylivuoto), sen hyödyntäminen koodin suoritukseen on huomattavasti
helpompaa kuin nykyaikaisessa, suojatussa binäärissä — ei tarvitse ohittaa
ASLR:ää, stack canaria eikä NX:ää, ja binäärin osoitteet ovat kiinteitä joka
käynnistyskerralla.

Lisäksi tuotantofirmwaresta löytyy `bin/gdbserver` — debug-työkalu, joka ei
kuulu tuotantoversioon ja joka mahdollistaisi prosessin etädebuggauksen, mikäli
hyökkääjä saisi sen käynnistettyä.

### 3.2 Ei perinteistä root-salasanaa / OS-tason autentikointia

Purussa ei löytynyt `/etc/passwd`- eikä `/etc/shadow`-tiedostoa, eikä
perinteistä `getty`/`login`/`inittab`-pohjaista konsolikirjautumisketjua.
`strings`-haku ei löytänyt viittauksia `/dev/console`- tai `/dev/tty`-pohjaiseen
kirjautumiseen `main`-binääristä.

Sen sijaan koko käyttöjärjestelmä näyttää rakentuvan yhden monoliittisen
`bin/main`-binäärin ympärille, joka toimii todennäköisesti myös init-prosessina
ja hoitaa autentikoinnin kahdella sovellustason mekanismilla:

- **Web-hallintapaneeli** (`/www/admin/Login.htm`): HTTP Digest -autentikointi
  MD5-algoritmilla (`http_do_login`, `http_match_user_auth`).
- **Pilviautentikointi**: TP-Link-tiliin sidottu JWT-pohjainen kirjautuminen
  (`cloud_iot`, `/v2/auth/device`, merkkijono `"Device not auth or jwt empty,
  isAuth:%d"`).

**Johtopäätös:** perinteistä murrettavaa root-salasanahashia ei tästä
purusta löytynyt, koska sellaista ei tallenneta tiedostojärjestelmään lainkaan.
Tämä on itsessään hyvä suunnitteluratkaisu verrattuna laitteisiin joissa on
kiinteä oletussalasana. _(Konsolin/UART-pääsyn todellista suojaustasoa ei
tässä työssä testattu fyysisesti laitteella — ks. jatkotutkimus, kohta 5.)_

### 3.3 Suodattamaton `popen()`-kutsu — mahdollinen komentoinjektio

Funktio `onboarding_execute_shell_cmd` (osoite `0x661414` binäärissä) sisältää
seuraavan, olennaisen koodinpätkän (Ghidra-dekompilaatio):

```c
undefined4 onboarding_execute_shell_cmd(char *param_1, void *param_2, ...) {
    FILE *__stream;
    ...
    if (param_1 == (char *)0x0) {
        return 0xffffffff;
    }
    __stream = popen(param_1,"r");
    ...
}
```

Funktion ensimmäinen parametri (`param_1`, suoraan komentomerkkijono) annetaan
`popen()`-kutsulle **ilman minkäänlaista syötteen suodatusta tai
whitelistausta**. Mikäli tähän parametriin päätyisi hyökkääjän kontrolloimaa
dataa (esim. shell-metamerkkejä `;`, `|`, `` ` ``, `&&`), seurauksena olisi
mielivaltaisen komennon suoritus laitteella.

Funktiolla on kolme kutsupaikkaa binäärissä. Yksi niistä jäljitettiin
funktioon `wlan_ap_start`, jossa kutsu tapahtuu näin:

```c
strcpy(acStack_128,"ifconfig wlan1 | grep addr:");
onboarding_execute_shell_cmd(acStack_128, local_1a8, ...);
```

Tässä nimenomaisessa kutsussa komento on **kovakoodattu merkkijono**, ei
käyttäjän syötettä — tämä yksittäinen kutsu ei siis ole hyödynnettävissä.

Kahta muuta kutsupaikkaa ei ehditty jäljittää loppuun asti tässä työn
vaiheessa (ks. kohta 5, jatkotutkimus). Funktion `wlan_ap_update_ssid`
tarkastelu osoitti, että SSID-arvo kulkee sisäisen tietovaraston
(`ds_read`/`ds_advanced_write`) kautta erilliseen, vielä analysoimattomaan
funktioon (`FUN_0065d494`) ennen kuin sen mahdollinen yhteys
`onboarding_execute_shell_cmd`-kutsuun on varmistettavissa.

**Johtopäätös:** `onboarding_execute_shell_cmd`-funktio on suunnittelultaan
vaarallinen (suodattamaton `popen()`), ja se on todistettavasti käytössä
useammassa kuin yhdessä kutsukohdassa. Yhden kutsun turvallisuus varmistettiin;
kahta muuta ei ehditty varmistaa. Tämä on merkittävä löydös riippumatta
lopullisesta hyödynnettävyydestä, koska se osoittaa riskialttiin
ohjelmointikäytännön olevan käytössä laitteen koodikannassa laajemminkin.

## 4. Yhteenveto ja arvio turvallisuudesta

| Löydös | Vakavuus | Vahvistettu? |
|---|---|---|
| Puuttuvat binary hardening -suojaukset (RELRO/canary/NX/PIE) | Korkea (mahdollistaa muiden haavoittuvuuksien hyödyntämisen) | Kyllä |
| gdbserver mukana tuotantofirmwaressa | Matala–keskitaso | Kyllä |
| Ei perinteistä root-salasanaa | Positiivinen löydös (ei kiinteää oletustunnusta) | Kyllä |
| Suodattamaton `popen()` shell-komentofunktiossa | Korkea, jos hyödynnettävissä | Osittain — yksi kutsu turvallinen, kaksi vahvistamatta |

Kokonaisarviona laite noudattaa osittain hyviä käytäntöjä (ei kiinteää
oletussalasanaa, pilviautentikointi), mutta binäärin täydellinen
suojausmekanismien puute ja vaarallisesti suunnitellun
`onboarding_execute_shell_cmd`-funktion olemassaolo ovat merkittäviä riskejä.
Mikäli jompikumpi jäljittämättä jäänyt kutsu osoittautuisi hyödyntää
käyttäjän/hyökkääjän kontrolloimaa syötettä, laitteessa olisi täysi etäkäyttöinen
komentoinjektio.

## 5. Jatkotutkimus (tehdään seuraavaksi)

- [ ] Jäljitä `onboarding_execute_shell_cmd`-funktion kaksi muuta kutsupaikkaa
      Ghidrassa asti lähteeseen (tuleeko parametri käyttäjän hallitusta
      syötteestä, esim. WiFi-SSID:stä tai HTTP-pyynnöstä).
- [ ] Analysoi `FUN_0065d494` (SSID-käsittelyn jatkofunktio).
- [ ] Puretaan ja verrataan myös virallista, ladattua firmware-pakettia
      (`Tapo_C200v4_en_1.4.2.bin`) `tp-link-decrypt`-työkalulla — selvitetään
      onko siinä sama rootfs-salausratkaisu vai eroaako se dump-tiedostosta.
- [ ] Jos aikaa riittää: kokeile käytännössä hyödynnettävyyttä (esim.
      ylipitkä SSID-arvo onboarding-vaiheessa) staattisessa/emuloidussa
      ympäristössä.
